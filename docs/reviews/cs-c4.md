## 改了没报的

- 汇报说「栈第一次非空时展开」，实际是 `open={stackSize>0}`（`packages/sim/src/Cpu.tsx:78`）：每次由空变不空就展开，变空就收起；读者手动收起以后，只要栈一直不空就不会再自动打开。这符合方案「栈不空时栈面板也默认展开」，不用改。
- 流水线里的自修改代码按顺序执行的结果算。`packages/sim/src/core/pipeline.ts:58`–`61` 每取一条指令就在私有状态上把它执行完，后面的取指看到的是它改过的内存。`pipeline.test.ts:55` 测的 `LDI R0, 0` / `ST R0, [next]` / `next: OUT R0` / `HLT` 得 3 条、没有输出。按真实的五级流水线，`ST` 第 5 拍到 MEM 才写内存，`next` 第 3 拍就取进来了，取到的还是 `OUT R0`，会输出 [0]、完成 4 条。两种都说得通；现在的做法让流水线的结果永远和 cpu 一样，我同意保留。但这条约定会改变答案，汇报只说「有独立用例」，`plan.md` 附录 C 流水线那一格和「我替你定的」都没写。不用改代码，合并时我把「附录 C 补一句」记进 C5 的「顺带」。

## 值得一提的

- 缓存、cpu 接缓存、流水线三个内核和我写方案时的独立参照逐次一致。其中一处是我的参照错了：方案写的是「跳了就冲掉」，跳转目标恰好是下一条时 GPT 也冲掉；我原来的参照只在目标不是 PC + 2 时才冲，改成按条件成不成立以后才一致。按方案的字面意思 GPT 是对的，读者也好记：条件成立就冲。
- 停顿拍数那 4 段的差别：一条指令在 ID 里等数据的同一拍，前面的分支在 EX 里决定跳，它被冲掉。我的参照把这一拍也算一次数据停顿，GPT 不算。GPT 每拍先决定 ID 里的指令能不能进 EX，再看 EX 里的分支；被冲掉的指令等不到「进 EX」那一拍，也就不算停顿。两边的时序图完全一样，GPT 的算法更合理。
- 流水线没有另写一套执行，每取一次指就用 C3 的 P8 内核在私有状态上执行，到 WB 才提交。所以错路上的 IN、OUT、HLT、非法指令都漏不到结果里，随机测试能直接拿 cpu 的结果当标准答案。代价就是上面那条自修改代码的约定。
